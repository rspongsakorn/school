# เลือกรายการที่ชำระในใบแจ้ง (ชำระทีละรายการ)

วันที่ 2026-11-26 · ขนาด: โครงการ · อนุมัติแนวทางในบทสนทนาแล้ว (วิธีที่ 1)

## ที่มา

ผู้ปกครองบางรายชำระไม่ครบ เช่น ยังไม่จ่ายค่าห้องปรับอากาศ ทุกวันนี้หน้ารับชำระให้กรอกแค่ยอดเงิน
ระบบผูกการชำระไว้ระดับใบแจ้ง (`payment_allocations` มีแค่ `invoice_id`, `amount`)
ใบเสร็จจึงเฉลี่ยยอดลงทุกรายการตามสัดส่วน (`src/lib/finance/receipt-line-items.ts`)
และรายงานค้างชำระบอกได้แค่ "ค้าง 1,500" ไม่บอกว่าค้างค่าอะไร โรงเรียนจึงตามเก็บยาก

## เป้าหมาย

- หน้ารับชำระ (ทีละใบ) ให้ติ๊กเลือกรายการที่ผู้ปกครองจ่าย ยอดเงินคือผลรวมของรายการที่ติ๊ก
- ใบเสร็จแสดงเฉพาะรายการที่จ่ายจริง ด้วยยอดจริง ไม่เฉลี่ย
- ครั้งถัดไปที่รับชำระ หน้ารับชำระแสดงเฉพาะรายการที่ยังค้าง
- รายงานค้างชำระ (`/reports/outstanding`) มีคอลัมน์ "รายการที่ค้าง" บอกชื่อรายการที่ยังไม่จ่าย

## ไม่ทำในรอบนี้

- จ่ายบางส่วนของรายการเดียว (เช่น ค่าห้องปรับอากาศ 3,000 จ่าย 1,000) — **ห้าม** ตามที่ผู้ใช้กำหนด
- ใบแจ้งหนี้ที่พิมพ์ไปทวงผู้ปกครอง
- เลือกรายการในหน้ารับชำระหลายใบพร้อมกัน (ยังจ่ายทั้งยอดที่เหลือของแต่ละใบ)
- นำเข้า CSV/XLSX ย้อนหลัง (ยังบันทึกระดับใบแจ้งเหมือนเดิม)
- ระบุรายการย้อนหลังให้การชำระบางส่วนที่บันทึกไปแล้ว
- ให้ส่วนลดในการชำระครั้งที่สองขึ้นไป (กฎเดิม: ส่วนลดได้เฉพาะใบที่ยังไม่เคยชำระ)

## สิ่งที่ถือว่าล้มเหลว แม้ระบบจะทำงาน

- ยกเลิกใบเสร็จแล้ว รายการที่เคยจ่ายไม่กลับมาเป็นค้าง หรือยอดค้างของใบแจ้งไม่ตรงกับผลรวมรายการที่ค้าง
- การลงบัญชีแยกประเภทเปลี่ยนไปจากเดิม
- ใบเก่าที่ชำระบางส่วนไว้แล้ว รับชำระส่วนที่เหลือไม่ได้

## ข้อจำกัดที่มีอยู่

- รายการในใบแจ้งแก้ไม่ได้หลังมีการชำระ (`changeInvoicePriceTier` ปฏิเสธเมื่อ `paid_amount > 0`) ยอดรายการจึงคงที่
- ส่วนลดตอนรับชำระเก็บแยกรายการใน `payment_discounts (payment_id, invoice_line_id, amount)` และทำให้ `student_invoices.total_amount = subtotal − ส่วนลด`
- `record_payment` (RPC, `20260703000000_record_payment_validation.sql`) ทำทุกอย่างในธุรกรรมเดียว
- `voidPayment` คืนยอดใบแจ้งจากฝั่งแอป ไม่ได้อยู่ในธุรกรรมเดียว — จึงไม่ควรเก็บสถานะรายการไว้ในที่ที่ต้องแก้ตอนยกเลิก
- บัญชีแยกประเภท: การรับชำระลง Dr เงินสด/ธนาคาร, Dr ส่วนลด (ตามรายการ), Cr ลูกหนี้ ไม่ขึ้นกับว่าจ่ายรายการไหน จึงไม่ต้องแก้
- กติกาโปรเจกต์: ทำบน branch แยก ไม่ merge เข้า main, `.env.local` ชี้ฐานจริง ห้ามทดสอบเขียนข้อมูลบนฐานนั้น

## แนวทางที่พิจารณา

1. **ตารางบันทึกรายการที่ชำระ (เลือกแล้ว)** — ตารางใหม่หนึ่งแถวต่อหนึ่งรายการที่จ่ายในการชำระหนึ่งครั้ง
   รายการค้างคำนวณจาก "รายการที่ไม่มีแถวของการชำระที่ยัง active" ยกเลิกใบเสร็จแล้วถูกต้องเอง
   ข้อเสีย: รายงานต้องอ่านเพิ่มอีกหนึ่งตาราง
2. **ช่อง "ชำระแล้ว" บน `invoice_lines`** — อ่านง่าย แต่ต้องแก้ทุกครั้งที่รับชำระและยกเลิก
   และ `voidPayment` ไม่ได้อยู่ในธุรกรรมเดียว ข้อมูลอาจเพี้ยนแบบมองไม่เห็น — ไม่เลือก
3. **แยกรายการที่ค้างเป็นใบแจ้งใหม่** — เลขเอกสารและรายงานยุ่ง — ตัดทิ้ง

ผู้ใช้เลือกวิธีที่ 1

## การออกแบบ

### ข้อมูล

ตารางใหม่ `payment_line_allocations`:

| คอลัมน์ | ความหมาย |
|---|---|
| `id` | uuid |
| `payment_id` | FK `payments`, ON DELETE RESTRICT |
| `invoice_line_id` | FK `invoice_lines`, ON DELETE RESTRICT |
| `amount` | ยอดที่จ่ายของรายการนี้ = ยอดรายการ − ส่วนลดของรายการนี้ในการชำระเดียวกัน (≥ 0) |
| `created_at` | |

- UNIQUE (`payment_id`, `invoice_line_id`)
- RLS แบบเดียวกับ `payment_discounts` ทุกประการ (admin/finance `FOR ALL`, ครูอ่านได้ตามเดิม)
  เพราะ `record_payment` เป็น `SECURITY INVOKER` ต้องเขียนตารางนี้ได้ด้วยสิทธิ์ของผู้ใช้ *(การตัดสินใจของผู้ออกแบบ)*
- ผลรวม `amount` ของการชำระหนึ่งครั้ง = `payment_allocations.amount` ของการชำระนั้น

**ใบแจ้งแบบติดตามรายการ** คือใบที่ครบทั้งสองข้อ:
1. การชำระ active ทุกครั้งมีแถวใน `payment_line_allocations` (รวมถึงใบที่ยังไม่เคยชำระ)
2. ไม่มีส่วนลดระดับใบแจ้ง หรือการปิดใบโดยไม่เก็บเงิน (`student_invoices.discount_value` ว่างหรือ 0)

ใบที่ไม่ครบคือ **ใบแบบเดิม** *(ข้อ 2 เป็นการตัดสินใจของผู้ออกแบบ: ใบที่มีส่วนลดระดับใบ เช่นจากการนำเข้า XLSX
มี `total_amount` น้อยกว่าผลรวมรายการ ติ๊กครบทุกรายการจะเกินยอดและ RPC ปฏิเสธ จึงให้ใช้วิธีกรอกยอดเดิม)*

**รายการที่ค้าง** ของใบแบบติดตามรายการ = รายการใน `invoice_lines` ที่ไม่มีแถวใน
`payment_line_allocations` ที่ผูกกับการชำระ `status = 'active'`
รายการยอด 0 บาทนับว่าไม่ค้าง (ไม่ต้องให้เลือก)

### บันทึกการชำระ

- `record_payment` รับพารามิเตอร์ใหม่ `p_line_ids uuid[]` (ใส่ค่าเริ่มต้น NULL เพื่อไม่ทำลายผู้เรียกเดิม)
- เมื่อมี `p_line_ids`:
  - ทุกรายการต้องอยู่ในใบนี้ และยังค้าง (ตรวจในธุรกรรมหลัง `FOR UPDATE` ใบแจ้ง)
  - ใบต้องเป็นแบบติดตามรายการ
  - `p_amount` ต้องเท่ากับผลรวม (ยอดรายการ − ส่วนลดของรายการนั้น) ของรายการที่เลือก
  - ส่วนลดใน `p_discounts` ต้องอยู่บนรายการที่เลือกเท่านั้น
  - เขียนแถว `payment_line_allocations` ในธุรกรรมเดียวกัน
- เมื่อ `p_line_ids` เป็น NULL: ทำงานเหมือนเดิม **เฉพาะใบแบบเดิม** ถ้าใบเป็นแบบติดตามรายการ ให้ปฏิเสธ
  เพื่อไม่ให้ใบที่ติดตามอยู่กลายเป็นใบแบบเดิมโดยไม่ตั้งใจ *(การตัดสินใจของผู้ออกแบบ)*
- การนำเข้าย้อนหลัง (`record_backfill_payment`) เป็น RPC แยก ไม่แก้ ถ้านำเข้าการชำระลงใบแบบติดตามรายการ
  ใบนั้นจะกลายเป็นใบแบบเดิม ยอมรับได้เพราะเป็นข้อมูลย้อนหลัง
- ฝั่งแอป (`recordPayment`, `executeRecordPayment`) ตรวจซ้ำแบบเดียวกันก่อนเรียก RPC
  และเลิกกฎ "มีส่วนลดต้องชำระเต็มยอดสุทธิ" สำหรับใบแบบติดตามรายการ — เปลี่ยนเป็น "ยอดต้องเท่ากับผลรวมรายการที่เลือกหลังหักส่วนลด"
- สถานะใบแจ้งยังคิดจาก `paid_amount` กับ `total_amount` เหมือนเดิม

### หน้ารับชำระทีละใบ

มีสองจุดที่รับชำระทีละใบผ่าน `recordPayment` ต้องแก้ทั้งคู่ให้ทำงานเหมือนกัน
(แยกส่วนเลือกรายการเป็นคอมโพเนนต์ใช้ร่วมกันได้):
- ปุ่มชำระในหน้าใบแจ้ง (`src/components/finance/invoice-payment-dialog.tsx`)
- หน้ารับชำระ `/payments` (`src/components/finance/payments-panel.tsx` ราวบรรทัด 516)

ใบแบบติดตามรายการ:

```
ใบแจ้ง: ค่าธรรมเนียม 2/69                ค้าง 12,000
[x] ค่าเทอม            [ส่วนลด] บาท    8,000
[x] ค่าอาหาร           [ส่วนลด] บาท    2,500
[ ] ค่าห้องปรับอากาศ   [ส่วนลด] บาท    1,500
                         ยอดที่ชำระ  10,500
```

- แสดงเฉพาะรายการที่ค้าง ติ๊กไว้ทุกรายการเป็นค่าเริ่มต้น
- ช่องยอดเงินอ่านอย่างเดียว คำนวณจากรายการที่ติ๊กหักส่วนลด
- ช่องส่วนลดใช้ได้เฉพาะรายการที่ติ๊ก และเฉพาะเมื่อใบยังไม่เคยชำระ (กฎเดิม)
- ไม่ติ๊กเลยกดบันทึกไม่ได้

ใบแบบเดิม: หน้าตาเหมือนทุกวันนี้ (กรอกยอดเงินเอง) พร้อมข้อความสั้นว่า "ใบนี้ชำระบางส่วนก่อนมีการเลือกรายการ"

### หน้ารับชำระหลายใบ (`recordPaymentsBulk`)

ยังจ่ายยอดค้างทั้งหมดของแต่ละใบ ถ้าใบเป็นแบบติดตามรายการ ส่ง `p_line_ids` = รายการที่ค้างทั้งหมด
เพื่อให้ข้อมูลรายการครบ ใบแบบเดิมส่ง NULL

### ใบเสร็จ (`computeReceiptLineItems`, `src/lib/data/receipt-print.ts`)

- ถ้าการชำระมีแถว `payment_line_allocations`: แสดงรายการเหล่านั้นด้วยยอดรายการเต็ม และส่วนลดแยกเหมือนเดิม
- ถ้าไม่มี: ใช้ตรรกะเดิม (เต็มรายการหรือเฉลี่ย)
- ใบเสร็จที่ออกไปแล้วไม่เปลี่ยน

### รายงานค้างชำระ (`fetchOutstandingReport`, `outstanding-report-panel.tsx`)

- คอลัมน์ใหม่ "รายการที่ค้าง" ทั้งมุมมองตารางและแบบรายชื่อ และในหน้าพิมพ์
- ใบแบบติดตามรายการที่ชำระบางส่วน: ชื่อรายการที่ค้างคั่นด้วย ", "
- ใบที่ยังไม่ชำระเลย: เว้นว่าง (ค้างทุกรายการ)
- ใบที่ชำระครบ: เว้นว่าง
- ใบแบบเดิมที่ชำระบางส่วน: "ไม่ระบุ (ชำระก่อนระบบใหม่)"
- ดึงข้อมูลเป็นชุด (ใช้ตัวช่วยแบ่งชุด id ที่มีอยู่ เช่น `map-limit`/`paginate`) ไม่ยิงทีละใบ

### ยกเลิกใบเสร็จ

ไม่ต้องแก้ แถว `payment_line_allocations` ของใบเสร็จที่ยกเลิกถูกตัดออกเพราะกรองเฉพาะการชำระ `active`

พฤติกรรมเดิมที่คงไว้: ยกเลิกใบเสร็จที่มีส่วนลด `voidPayment` คืน `total_amount` เป็น `subtotal`
ถ้าใบนั้นมีการชำระครั้งหลังอยู่แล้ว รายการที่กลับมาค้างจะค้างเต็มราคา และให้ส่วนลดใหม่ไม่ได้ (กฎ "ส่วนลดเฉพาะใบที่ยังไม่ชำระ")
ตัวเลขยังตรงกัน ทางแก้คือยกเลิกใบเสร็จครั้งหลังก่อน แล้วรับชำระใหม่พร้อมส่วนลด

### บัญชีแยกประเภทและการปิดใบโดยไม่เก็บเงิน

- การลงบัญชีรับชำระไม่เปลี่ยน
- การปิดใบโดยไม่เก็บเงิน (`record_backfill_invoice_discount`, เช่น ยกเว้นค่าประกัน) ยังเฉลี่ยตามสัดส่วนรายการเหมือนเดิม
  ใบที่ผ่านเส้นทางนี้มี `discount_value` จึงกลายเป็นใบแบบเดิมตามนิยามข้างบน ไม่ซ้อนกับการติดตามรายการ

## การทดสอบ

- ฟังก์ชันล้วน (Vitest): คำนวณรายการที่ค้าง, แยกใบแบบติดตาม/แบบเดิม, ยอดที่ต้องชำระจากรายการที่เลือกและส่วนลด, ใบเสร็จจากแถวรายการ, ข้อความคอลัมน์รายงาน
- RPC: ทดสอบบนฐานทดสอบเท่านั้น — เลือกรายการที่ไม่ใช่ของใบ, รายการที่จ่ายแล้ว, ยอดไม่ตรง, ส่วนลดบนรายการที่ไม่ได้เลือก ต้องถูกปฏิเสธ
- ไล่ในเบราว์เซอร์บนฐานทดสอบ: จ่าย 2 ใน 3 รายการ → ใบเสร็จ → รายงานแสดง "ค่าห้องปรับอากาศ" → จ่ายส่วนที่เหลือ → ยกเลิกใบเสร็จแรก → รายการกลับมาค้าง
- รัน `scripts/verify-gl-invariants.mjs` หลังทดสอบ ยืนยันบัญชีไม่เปลี่ยน
